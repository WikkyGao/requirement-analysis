# 系统概要说明书模板

> 由 `scripts/prd_generator.py --doc-type system-overview` 生成。
> 面向架构评审与项目立项，描述"系统整体做什么、由哪些部分组成、边界在哪"。
> 与详细说明书的区别：本文档只到模块与接口概要层，不展开字段与实现细节。

---

## 章节结构

| 章节 | 内容 | 主要输入 |
|------|------|----------|
| 1. 引言 | 编写目的、适用范围、术语、参考资料 | `purpose` / `scope` / `glossary` / `references` |
| 2. 系统概述 | 项目背景、建设目标、用户角色、运行环境 | `background` / `goals` / `roles` / `architecture` / `runtime_env` |
| 3. 总体设计 | 设计原则、系统架构、模块划分 | `design_principles` / `architecture` / `features` |
| 4. 功能概要 | 功能清单、核心业务流程 | `features` |
| 5. 接口概要 | 外部/内部接口清单 | `interfaces` |
| 6. 数据概要 | 主要实体、实体关系 | `entities`（缺省由 `features[].fields` 推导） |
| 7. 非功能需求 | 性能、安全、可用性等基线 | `nfr_baseline`（缺省使用默认基线） |
| 8. 约束与假设 | 约束条件、前提假设 | `constraints` / `assumptions` |
| 附录 | 待确认事项、变更历史 | `pending_items` |

---

## 输出样例

```markdown
# 电商平台 系统概要说明书

> 版本: v1.0.0 | 更新日期: 2026-10-21 | 文档类型: 系统概要说明书

## 1. 引言

### 1.1 编写目的

本文档描述电商平台的总体架构、模块划分与功能范围，作为详细设计与开发实施的依据。

### 1.2 适用范围

覆盖用户、商品、订单、支付四个业务域；不含商家后台与物流履约。

### 1.3 术语与缩略语

| 术语 | 说明 |
|------|------|
| SKU | 最小库存单位 |
| GMV | 成交总额 |

## 2. 系统概述

### 2.1 项目背景

现有系统无法支撑多商户经营，订单处理依赖人工，亟需重构。

### 2.2 建设目标

- 支持多商户入驻与统一结算
- 订单全流程自动化，人工介入率低于 5%
- 峰值支撑 1000 TPS

### 2.3 用户角色

| 角色 | 职责说明 |
|------|----------|
| 消费者 | 浏览商品、下单、支付、售后 |
| 平台运营 | 商户审核、活动配置、数据看板 |
| 商户 | 商品维护、订单发货、对账 |

### 2.4 运行环境

- **技术栈**: Java 17、Spring Boot、MySQL、Redis
- **部署方式**: 容器化部署，Kubernetes 编排
- **运行环境**: 待补充（服务器、操作系统、中间件、网络要求）

## 3. 总体设计

### 3.1 设计原则

- 职责单一：模块边界清晰，避免跨模块耦合
- 可扩展：预留功能扩展与容量扩展能力

### 3.2 系统架构

- **架构风格**: 分层单体（后续可拆分微服务）
- **技术栈**: Java 17、Spring Boot、MySQL、Redis
- **部署方式**: Kubernetes

**分层结构**

| 层次 | 职责 |
|------|------|
| 接入层 | 网关、鉴权、限流 |
| 应用层 | 业务编排与事务控制 |
| 领域层 | 核心业务规则 |
| 基础设施层 | 数据访问、消息、缓存 |

**核心组件**

| 组件 | 说明 |
|------|------|
| 订单服务 | 下单、取消、状态流转 |

### 3.3 模块划分

| 序号 | 模块 | 功能项数 | 主要功能 |
|------|------|----------|----------|
| 1 | 用户管理 | 4 | 注册、登录、实名、地址 |
| 2 | 订单管理 | 6 | 下单、支付、取消、退款 |

## 4. 功能概要

### 4.1 功能清单

| 编号 | 功能 | 所属模块 | 优先级 | 功能描述 |
|------|------|----------|--------|----------|
| F-001 | 用户注册 | 用户管理 | high | 支持邮箱/手机号注册 |

### 4.2 核心业务流程

- **用户注册**: 填写信息 → 校验唯一性 → 发送验证码 → 激活账号
- **创建订单**: 选择商品 → 校验库存 → 生成订单 → 发起支付

## 5. 接口概要

| 接口名称 | 类型 | 提供方 | 调用方 | 说明 |
|----------|------|--------|--------|------|
| 创建订单接口 | HTTP | 订单服务 | 前端 | POST /orders |
| 支付回调 | HTTP | 支付网关 | 订单服务 | POST /payments/callback |

## 6. 数据概要

### 6.1 主要实体

| 实体 | 表名 | 说明 | 字段数 |
|------|------|------|--------|
| 用户 | t_user | 用户主数据 | 12 |
| 订单 | t_order | 订单主数据 | 20 |

### 6.2 实体关系

- **用户**: 一个用户拥有多个订单（1:N）
- **订单**: 一个订单包含多个订单明细（1:N）

## 7. 非功能需求

> 以下为默认基线（待确认），如无特殊场景可直接沿用。

| NFR 项 | 默认基线 | 触发特殊提问的条件 |
|--------|----------|--------------------|
| 并发量 | 按日均 1000 UV 设计 | 大促/高并发场景 |
| 数据保留 | 永久保留 / 按合规保留 3 年 | 金融、审计、隐私合规特殊要求 |
| 删除操作 | 软删除 + 操作日志 | 不可恢复/强审计需求 |
| 安全加密 | 常规传输加密 | 金融级加密、支付密钥等 |
| 可用性 | 常规（99.9%） | 用户明确 SLA 要求 |

## 8. 约束与假设

### 8.1 约束条件

- 支付渠道仅接入微信支付与支付宝
- 首期不建设自建物流

### 8.2 前提假设

- 商户资质由人工审核
- 历史数据通过离线脚本迁移

## 附录

### 待确认事项

- 待确认峰值并发口径

### 变更历史

| 版本 | 日期 | 变更内容 | 变更人 |
|------|------|----------|--------|
| v1.0.0 | 2026-10-21 | 初始版本 | - |
```

## 写作要求

1. **只写概要**：模块职责、接口清单、实体清单到"能看懂整体"即可，字段与流程细节留给详细说明书。
2. **架构必须落到图或表**：用分层表 + 组件表表达，避免只有形容词。
3. **非功能需求必须量化**：无法量化的写"待确认"，不要写"高性能""高可用"。
4. **与 PRD 对齐**：功能编号、模块名称、优先级必须与 PRD 一致。
