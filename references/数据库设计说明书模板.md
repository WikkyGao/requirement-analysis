# 数据库设计说明书模板

> 由 `scripts/prd_generator.py --doc-type database-design` 生成。
> 面向后端开发与 DBA，描述"数据怎么存、表怎么建、索引与约束怎么加"。
> 实体来源优先级：`entities` 显式定义 > `features[].fields` 自动推导。

---

## 章节结构

| 章节 | 内容 | 主要输入 |
|------|------|----------|
| 1. 引言 | 编写目的、适用范围、术语、参考资料 | `purpose` / `scope` / `glossary` |
| 2. 设计概述 | 设计原则、选型与环境、命名规范、类型规范 | `db_principles` / `database` / `charset` / `collation` / `timezone` |
| 3. 逻辑数据模型 | 实体清单、实体关系 | `entities` / `entity_relations` |
| 4. 物理表设计 | 逐表：表属性、字段表、索引设计 | `entities[]` |
| 5. 数据字典 | 跨表字段的标准定义 | 由实体字段汇总 |
| 6. 索引与约束设计 | 索引策略、约束策略 | `index_strategy` / `constraint_strategy` |
| 7. 初始化与迁移 | 初始化数据、版本迁移 | `init_data` / `migration_strategy` |
| 8. 安全与权限 | 数据安全、权限、容量与备份 | `data_security` / `permission_design` / `nfr_baseline` |
| 附录 | 待确认事项、变更历史 | `pending_items` |

---

## 输入数据结构

```json
{
  "entities": [
    {
      "name": "用户",
      "table_name": "t_user",
      "description": "用户主数据",
      "primary_key": "id",
      "fields": [
        {"name": "id", "type": "bigint", "required": true, "primary_key": true, "description": "主键"},
        {"name": "email", "type": "varchar", "length": 128, "required": true, "description": "登录邮箱"},
        {"name": "status", "type": "tinyint", "length": 1, "required": true, "default": "1", "description": "状态：0 禁用 / 1 正常"}
      ],
      "indexes": [
        {"name": "uk_user_email", "type": "唯一索引", "fields": ["email"], "description": "邮箱唯一"}
      ],
      "relations": ["与 t_order 为 1:N"]
    }
  ],
  "entity_relations": [
    {"from": "t_user", "to": "t_order", "type": "1:N", "description": "一个用户拥有多个订单"}
  ]
}
```

未提供 `entities` 时，脚本会把每个带 `fields` 的功能项视为一张表：
表名优先取 `table_name`，否则由功能编号推导（如 `F-001` → `t_f_001`）。

## 输出样例

```markdown
# 电商平台 数据库设计说明书

> 版本: v1.0.0 | 更新日期: 2026-10-21 | 文档类型: 数据库设计说明书

## 1. 引言

### 1.1 编写目的

本文档定义电商平台的核心数据模型、表结构与索引策略，作为建表与数据访问层开发的依据。

## 2. 设计概述

### 2.1 设计原则

- 满足第三范式，必要时为查询性能做冗余
- 所有表统一主键、创建时间与更新时间字段
- 不使用物理外键，关联关系由应用层保证
- 敏感字段加密存储，禁止明文落库

### 2.2 数据库选型与环境

- **数据库**: MySQL 8.0
- **字符集**: utf8mb4
- **排序规则**: utf8mb4_general_ci
- **时区**: UTC+8

### 2.3 命名规范

| 对象 | 规范 | 示例 |
|------|------|------|
| 表名 | `t_` 前缀 + 小写下划线 | `t_user` |
| 字段名 | 小写下划线 | `created_at` |
| 主键 | 统一 `id` | `id` |
| 外键 | `<实体>_id` | `user_id` |
| 索引 | `idx_表名_字段` / `uk_表名_字段` | `idx_user_phone` |

### 2.4 数据类型规范

| 场景 | 类型 | 说明 |
|------|------|------|
| 主键 | `bigint unsigned` | 自增或雪花 ID |
| 短文本 | `varchar(n)` | 按实际长度设置，避免滥用 text |
| 长文本 | `text` / `longtext` | 富文本、日志等 |
| 金额 | `decimal(18,2)` | 禁止使用浮点类型 |
| 时间 | `datetime` | 精确到秒 |
| 布尔 | `tinyint(1)` | 0/1 |
| 枚举 | `varchar` + 字典表 | 避免数据库原生 enum |

## 3. 逻辑数据模型

### 3.1 实体清单

| 实体 | 表名 | 说明 | 字段数 |
|------|------|------|--------|
| 用户 | t_user | 用户主数据 | 12 |
| 订单 | t_order | 订单主数据 | 20 |

### 3.2 实体关系

- **t_user → t_order**（1:N）: 一个用户拥有多个订单
- **t_order → t_order_item**（1:N）: 一个订单包含多个明细

## 4. 物理表设计

### 4.1 t_user（用户）

| 中文名 | 用户 |
| 说明 | 用户主数据 |
| 主键 | `id` |

| 序号 | 字段名 | 类型 | 长度 | 允许空 | 默认值 | 约束/索引 | 说明 |
|------|--------|------|------|--------|--------|-----------|------|
| 1 | `id` | bigint | - | 否 | - | PK | 主键 |
| 2 | `email` | varchar | 128 | 否 | - | - | 登录邮箱 |
| 3 | `password_hash` | varchar | 255 | 否 | - | - | 密码哈希 |
| 4 | `status` | tinyint | 1 | 否 | 1 | IDX | 状态：0 禁用 / 1 正常 |
| 5 | `created_at` | datetime | - | 否 | CURRENT_TIMESTAMP | - | 创建时间 |
| 6 | `updated_at` | datetime | - | 否 | CURRENT_TIMESTAMP | - | 更新时间 |

**索引设计**

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| uk_user_email | 唯一索引 | email | 邮箱唯一 |
| idx_user_status | 普通索引 | status | 按状态筛选 |

### 4.2 t_order（订单）

...（同上结构）

## 5. 数据字典

| 字段名 | 类型 | 说明 | 所属表 |
|--------|------|------|--------|
| `id` | bigint | 主键 | t_user, t_order |
| `status` | tinyint(1) | 状态标识 | t_user, t_order |
| `created_at` | datetime | 创建时间 | t_user, t_order |

## 6. 索引与约束设计

### 6.1 索引策略

高频查询字段建立普通索引；唯一业务标识建立唯一索引；组合索引遵循最左前缀原则。

### 6.2 约束策略

主键非空唯一；业务唯一键由唯一索引保证；关联完整性由应用层校验。

## 7. 初始化与迁移

### 7.1 初始化数据

- 字典表、系统配置等基础数据随版本初始化
- 管理员账号首次启动时创建

### 7.2 版本迁移

每次结构变更提供可回滚的迁移脚本，按版本号顺序执行。

## 8. 安全与权限

### 8.1 数据安全

敏感字段加密存储，导出与查询遵循最小必要原则，操作留痕。

### 8.2 权限设计

按角色分配数据访问权限，应用账号仅授予必需的表级读写权限。

### 8.3 容量与备份

以下为默认基线（待确认）：

| NFR 项 | 默认基线 | 触发特殊提问的条件 |
|--------|----------|--------------------|
| 并发量 | 按日均 1000 UV 设计 | 大促/高并发场景 |
| 数据保留 | 永久保留 / 按合规保留 3 年 | 金融、审计、隐私合规特殊要求 |
| 删除操作 | 软删除 + 操作日志 | 不可恢复/强审计需求 |
| 安全加密 | 常规传输加密 | 金融级加密、支付密钥等 |
| 可用性 | 常规（99.9%） | 用户明确 SLA 要求 |

## 附录

### 待确认事项

- 待确认订单表是否需要分库分表
```

## 写作要求

1. **表名、字段名必须可落库**：中文名只放在说明中，不直接作为表名/字段名。
2. **主键、非空、默认值、索引四要素齐全**：缺一项视为设计未完成。
3. **金额禁止浮点**：统一 `decimal(18,2)`。
4. **状态字段必须写枚举含义**：如 `0 禁用 / 1 正常`。
5. **变更必须可回滚**：迁移脚本与回滚脚本成对维护。
